# universal-analytics

The charting and UI layer for the analytics MVP. A view is described once, as JSON, in marks, encodings and roles; the container it lands in decides how to present it. Tracking, storage and retrieval are built elsewhere, and this repo starts at the query result.

What follows is the vision, from `docs/vision.md`. Weigh every decision about scope or architecture against it, and where a rule below disagrees with it, raise that and do not settle it silently.

@docs/vision.md

Read `docs/view-grammar-reference.md` before changing the grammar, and `docs/milestones.md` for the course. `docs/chart-coverage-plan.md` is the plan that added the marks and layouts beyond the prototype's, and section 8 of it records what building each step found. `docs/uncommon-coverage-plan.md` is the plan that followed it, for the Uncommon chart types, and its section 7 is the same record. Sections of the reference are labelled Proven, Proposed or Open.

## Commands

```
pnpm install
pnpm test         # vitest: sweep, parity with the prototype, plan, fit, schema, golden scenes
pnpm typecheck    # tsc --noEmit, strict
pnpm test -u      # rewrite golden scenes; read the diff before committing it
pnpm bench        # the bench at localhost:5173, on Vite
pnpm bench:archive   # the bench as it was, with the pages it no longer has
pnpm --filter @unified-analytics/bench capture   # every sample × width × theme × height off the parts page, to apps/bench/captures/<time>/ (ignored by git)
pnpm --filter @unified-analytics/bench check     # hold the latest capture to the parts' promises (the fit rules, and cut, overlap, theme, steady); against=<capture> for what moved
pnpm --filter @unified-analytics/tokens generate   # rewrite packages/tokens/generated from its config
```

Packages export their TypeScript source and nothing is built for release yet. Vite serves the bench.

## Layout

- `packages/core`: types, presets and `expand`, the plan (`resolve`, which takes no size), the views of a spec with a `facet` (`facets` in `plan.ts`, a view for each value with the engine's totals and one domain for every scale), the board (`board.ts`: `boardViews` and `boardSelect`, with `select`, which folds a proposed selection into a filter, `holds`, which reads a filter against a row, and `whereOf`, the filter a datum is), the scene builders (ratios), the fit rules and the one function that reads them at a room with no browser (`fitTo` in `fit.ts`, and `viewAt`, which gives the plan and scene with it and follows a rule's fallback), the sizes in px that no token and no rule says (`sizes.ts`), the tldr prose, `explain` (why a view looks as it does at a room, each decision tied to the place in the spec that caused it and the lever that changes it, with `selectedBecause` for what a surface adds of a selection), what each mark reads in each layout, as data that `resolve` holds every layer to (`READS` in `reads.ts`), which encoding each guide is read off (`GUIDES` in `guides.ts`), the registry for custom marks (`marks.ts`) and the one for the presets their packages register (`registerPreset` in `presets.ts`), and JSON Schemas in `schema/`, for a view, a catalog and a board.
- `packages/fixtures`: the catalog, the seeded fixture query engine (`typical`, `no-prior`, `empty`; it answers a query's `where` from the pairs it makes), the six sample specs the prototype knows (`samples`), the ones it does not (`moreSamples`) the ones with a `facet` (`facetSamples`, apart because a facet has no one plan for a sweep to ask for), and a board (`boardSamples`, apart because a board is no view). It registers the custom marks on import: `geo` with a small file of country shapes, `geo-tiles` and `geo-hexes` (the same mark with two files of tiles), `link` and `partition`.
- `packages/tokens`: build-time token generation, ported from the storybook repo. Base tier: Leonardo makes the colour ramps, the two arms of the diverging ramp among them (the sequential ramp is chosen by hand, in `config/sequential.json`), and Utopia the type, space and control-size scales; `config/base.tokens.json` holds the rest. Common tier: `config/common.tokens.json` (and `common.dark`) names the Spacefast library's variables as aliases into base. Charts tier: `config/charts.tokens.json` declares every `--ua-charts-*` token `<ua-view>` reads, as aliases into the other two. Style Dictionary compiles all three to `generated/tokens.css`. The bench loads it; `packages/dom` never imports it, and meets it only in those names (`test/dom-tokens.test.ts`).
- `test/`: one suite across the packages. There is no DOM in the run, so `packages/dom` is tested where it is strings and plain functions: the compiled rules, each layout's own rules, the measured pass's decisions, key stepping and the readout, and the path morph. The element is checked in a browser on the bench. Golden scenes are in `test/__snapshots__`. What the suites share (`run`, which gives a view's plan, scene and fit at a room; `shown`, which says that fit in short; `err`, `validView`, `ofUnbounded`, the sweep's cases and the scene helpers) is in `test/helpers.ts`, which is not itself a suite. Nothing in the run places a node in pixels: where a part lands is checked on the bench.
- `prototype/`: read-only reference. The tests load `prototype-bench.js` and hold the port to it.
- `apps/bench`: where work is looked at, and what GitHub Pages serves (`.github/workflows/bench.yml`). The playground, where a spec is written by hand and its view redrawn as it changes, on the fixture engine, with what the view says of itself (`UaView.explain()`) beside it; every sample in resizable frames, the ones with a facet after the rest, with data state and height limit as controls; a board, as the reference for a surface that draws one, where activating a row filters the other views (`board`: the page holds the board, runs each view's query and lays the views out, and lends Selected a look, which it has none of yet); the marks one at a time; one view at a ladder of widths in light and dark, with one of its parts picked out and a readout under each frame of the parts that show there (`parts`, for tuning a part against its container; `capture.ts` takes the same frames headless with Playwright, motion off, as pictures of each frame and each part and a `capture.json` of what `measure` read, so an evaluator reads a fixed snapshot; `check.ts` holds it to what each part promises, read off `FIT_RULES` by core's own `fitTo` and not restated, and writes `check.md` and `check.json` beside it; two captures of the same code agree frame for frame, so a frame that differs between them is a fault to find and not noise); and tokens (with elevation and the materials). The theme is one control at the nav's end on every page, kept in the browser (`src/theme.ts`). Every view is a `<ua-view>`; new painters, chrome and surfaces get a place here as they land. Paths in it are relative, so it builds for a subpath. What every page shares is said once: `src/setup.ts` registers the element and every painter (each custom mark's package gives one call for its own) and holds the merged samples; `src/page.ts` holds the page's own furniture with no library in it, so the tokens page loads none; `vite.config.ts` writes the theme's boot script (`src/theme-boot.js`) into every page's head, and the nav and the Data and Height controls where a page asks for them with a `<!-- bench:name -->` marker; a new page is built only once it is listed in its `PAGES`.
- `apps/bench-archive`: the bench as it was before it was cut down, kept to look back at and not changed: the demo, the sidebar, a dashboard for each of the seventeen plan goals (`goals`, on an engine and catalog of its own, which `test/goals.test.ts` reads), the analytics sidebar on Spacefast's live query API (`live`) and the spike. `pnpm bench:archive` serves it.
- `packages/dom`: the `<ua-view>` custom element and the fit-rule compiler. It plans once with no limits, paints the ratio scene, and leaves the fitting to container queries; a measured pass (`measure.ts`) settles what CSS cannot say. A spec with a `facet` it does not paint itself: it holds a `<ua-view>` for each value in a grid that wraps (`FACET_CSS` in `view.ts`), with the value's name over each. One module per layout in `src/layouts/`, behind the seam in `src/layout.ts`: `cartesian`, `rows`, `band`, `radial` and `matrix`, with `points`, `ranges` and `track` painting what those marks add. The furniture around the marks is in `src/chrome/`, one module each for the axes, the legend, the colour ramp, the key to sizes, the key to a unit's glyphs and the tooltip chip the readout and the crosshair share (`tip.ts`), with its stylesheet, which joins the base sheet once for every view, and the one function that paints it, which every layout and a custom mark's painter call. The swatch every key draws a colour with, and the pulse beside the number, is one rule set there (`swatch.ts`), and so is the one rule, its width, dash, hover and focus, that reference lines, segments, ticks, the crosshair and the hit all draw (`rule.ts`). So is a label placed in a plot, its tone, anchor, halo, cut and how a label the measured pass gives up is hidden (`label.ts`), with `thinLabels` in `measure.ts` the pass the axes, the line ends, the points, the rim and the Sankey's columns plug their collision rules into; the crosshair's chips and the treemap's names keep loops of their own. A custom mark's painter joins through `registerPainter`, and its keyboard and pointer through `roveItems`, the one interaction (`src/rove.ts`) the element's points and a grid's cells also have. `rove.ts` also names the states every atom has (`STATE`, and `IS` for a stylesheet): Interaction, Focus, Selected and Emphasis, as `docs/component-states-plan.md` sets them out. Its only dependency is core. `src/tokens.ts` lists the public tokens with the value each falls back to, which is the charts tier's own value except where `UNTHEMED` says why not (`test/dom-tokens.test.ts` holds both): colour, radius, stroke, opacity, weight, motion and the type faces. A face may be a fluid token; the element works each out once per view. Gaps, gutters and heights are not tokens: fit rules are worked out from them. The number is set in the dot matrix (`src/dots.ts`), wherever a view shows one: the prototype's 5 by 7 glyphs, drawn by the stylesheet on the view's own surface, with a cell of 4 px everywhere, as wide as its room.
- `packages/geo`: the `geo` custom mark, for a choropleth and symbols on a map. It offers its places, so a `text` layer says something on each region. The one package that depends on `d3-geo`. Its scene half loads with no DOM.
- `packages/flow`: the `link` custom mark, for a Sankey of one step, and its preset `sankey`. No dependency but core, and `packages/dom` for its painter. Its scene half loads with no DOM.
- `packages/partition`: the `partition` custom mark, for a treemap of one level or two. Squarify is written in it, and its only dependency is core (and `packages/dom`, for its painter). Its scene half loads with no DOM. The fixtures register it on import.
- `packages/spacefast`: the adapter from one answer of Spacefast's analytics query API to a view's query, result and catalog. One function, `adapt`. It knows that API's names; core still knows none. The API's two recorded examples are in `test/fixtures/spacefast`.
- `packages/dots`: not started.

## Rules

- **The core has no DOM and no framework.** Runtime dependencies are `d3-scale`, `d3-shape` and `d3-array`. Ask before adding any other.
- **Do not add chart types.** A new shape is a mark. A new combination is a preset, named after the `@automattic/charts` component it replaces where one exists. What the grammar cannot say is a custom mark, registered in code (`registerMark`), and each one counts against the grammar.
- **New samples go in `moreSamples`.** The parity tests sweep every entry of `samples` against the prototype. One with a `facet` goes in `facetSamples`: `resolve` refuses it, and the sweeps ask every sample for its plan.
- **Statistics come from the engine,** as companion fields (`metric@p25`). Core computes no quantile, bin or running total.
- **This is the candidate next major of `@automattic/charts`.** Keep its token structure, under our own prefix (`--ua-charts-*` for its `--a8c-charts-*`), and its keyboard model. The two do not interoperate yet; a page with version 4 tokens aliases each one across. See `docs/positioning.md`.
- **No sizes, breakpoints or presentation switches in a spec.** They belong to the container and its rules. `keep` is the author's one lever, and it is provisional.
- **Scenes carry paint tokens, never colours.**
- **Keys are stable and unique.** Transitions and keyboard navigation hang on them.
- **A node says where it is in one vocabulary** (reference, section 11 and Decided 51): `x` and `y` where it is, `x2` and `y2` its other end, `w` and `h` an extent, whatever its kind and its layout. A node that is built takes these and no name of its own for a place. `x` runs across from the start and `y` up from the bottom, for every node. A change to how nodes are placed is checked by comparing every sample's scene before and after, node for node, and by the capture: golden scenes change shape with it and prove nothing.
- **The catalog is an input.** Core functions take it as an argument; nothing in `packages/core` knows a metric name.
- **Totals come from the engine.** A view never sums the rows it receives to make a tldr value.
- **A board is data, and a selection is a filter.** A board (`board/0`, `packages/core/src/board.ts`) is views and the part of the query they share: its `query` is its params, with no variable or expression, and it has no layout and no state apart from itself (reference, Decided 49). `boardViews` gives each view's spec and what it marks, and `boardSelect` the board after a view proposes a selection. Views are combined by one rule with no field: a view is filtered by every dimension of the board's `where` but the ones it draws. `<ua-view>` proposes the filter a datum is and how it was activated on `ua-select` (`detail.where`, and `detail.how`: `pick`, `toggle` or `extend`, by the modifier held), and marks by the filter set on `selected`. What a proposal does to the selection is core's `select`, never the view's: a host folds it in (Decided 50). The element draws no board and fetches nothing. `test/board.test.ts` holds it.
- **A filter is the engine's.** A query's `where` holds dimensions to values (reference, section 5 and Decided 48); the engine applies it and carries it back as `meta.where`, and `resolve` refuses an answer that is not of its query's filter. Core filters no row and sums none. A view says its filter after its sentence and in `explain`, read off the answer. The fixture engine answers it from its pairs, within limits it names. `test/where.test.ts` holds all of it.
- **Every error names the fix.**
- **A guide is read off a scale.** `packages/core/src/guides.ts` says which encoding each guide comes from, and the plan has a view's guides from it whatever the layout: a guide that is built is added there, not to a layout. A key (a legend, a ramp, a key to sizes) may not leave before the marks it keys: a rule that takes one puts a shorter form in its place (`show`, or a switch in `set` the layout draws), takes the marks too, or has them drawn without the encoding (`plain` in `GUIDES`). `test/guides.test.ts` holds every rule to it, and a new rule that takes a key early fails there. A plot's ramp, for a metric on `color`, has the legend's switch for its marks (`split: plain`): it leaves with the axes and the bars and dots are then in one paint.
- **A mark reads what `READS` says.** `packages/core/src/reads.ts` lists the channels each mark reads in each layout and what each may hold (`READS`), the ones it is not drawn without (`NEEDS`) and the layer fields it has a use for (`FIELDS`), and `resolve` refuses what a layer says that is not there. A mark, a channel or a field that is built is added to it, and to the table in section 7 of the reference, in the same change. `test/reads.test.ts` holds the two together, and holds every cell to be one a sample draws or a probe there shows: add the probe with the cell. A custom mark states its own channels, in `reads`.
- **A mark is one function of its space** (reference, Decided 44). A view's space is two axes, each a list of values, a quantity or nothing, flat or bent about a centre, and a layout says what stands round the marks, not which marks may be drawn. So a mark that comes to be drawn in a second layout is drawn there by the function it has, handed that layout's places (`GRID_MARKS`, `LIST_MARKS`, `ROUND_MARKS` and `OVER_MARKS` in `scene.ts`), and painted by the painter it has (`paintLabels` and `paintPaths` in `packages/dom/src/layouts/points.ts`). It is not written again. A row's track draws the plot's `bar`, `rule`, `tick`, `dot` and `unit` so: each is the plot's function, handed one row, and what it makes is turned once (`turn`, `turnLayer` and `inTrack` in `scene.ts`), with what a list alone does to a mark said after the turn. A custom mark that offers its places (`places` in `marks.ts`) takes the plot's `text` over it the same way. The grid, the list, the circle and the map are done, and each stage was held to the bench's capture frame for frame.
- **A scale's domain goes through `common`** (`packages/core/src/scene.ts`). The views of a facet are read against one another, so each takes the widest domain any of them would take alone, named on its result (`Result.domains`). A scale that is added, in core or in a custom mark, passes what it would take through `common(result, name, own)`, or a facet of it draws each view to its own top. A whole (the shares of a pie) is its own and does not. `test/facet.test.ts` holds a plot, a list and a circle to it.
- **Parity with the prototype** is asserted by the sweep, for what takes no size: the engine's answer, the plan, the sentence and what each scene holds, node for node. Core places nothing (reference, Decided 43), so where a node lands is not compared; the tag `prototype-parity` is the last commit that did. If the prototype is wrong, flag it and change both the behaviour and that test on purpose; do not fix it silently. The prototype keeps its old names (`headline`, `sentence`, `host`); `test/core.test.ts` maps them to tldr value, tldr prose and container.
- **How a view gives way is data, and one function reads it.** A plan takes no size. The fit rules say what each part needs and what goes without it, `fitTo` reads them at a room for any surface, and the element's stylesheet is the same rules compiled. So a rule names every part it takes, one that stands inside another among them, and says which kind of view it is for (`mark`, `has`). A layout's painter adds CSS under a rule (`fit`) for how what is left is arranged, never for which parts show, and makes no rules of its own. `test/fit.test.ts` holds every sample at every room to it: a view is its number alone wherever a rule takes its marks, and no key goes while its marks stay. What only measuring decides is listed in the reference, section 10.2, and is owed as rules (Open 19).
- **Proposed items** in the reference are the plan: build them as written and report if they do not hold up. **Open items** are not yours to settle: raise them with a recommendation.
- **Small commits,** one concern each.
