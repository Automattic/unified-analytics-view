# universal-analytics

The charting and UI layer for the analytics MVP. A view is described once, as JSON, in marks, encodings and roles; the container it lands in decides how to present it. Tracking, storage and retrieval are built elsewhere, and this repo starts at the query result.

What follows is the vision, from `docs/vision.md`. Weigh every decision about scope or architecture against it, and where a rule below disagrees with it, raise that and do not settle it silently.

@docs/vision.md

Read `docs/view-grammar-reference.md` before changing the grammar: its sections are labelled Proven, Proposed or Open, and its section 19 is the log of what is decided and what is open. `docs/focus-plan.md` is the course since November 24, 2026: what is cut and what is built, a step at a time, with what each step found and what is still David's to decide. `docs/api-proposal.md` is what the views ask of the query API, for its owners: nothing in it is agreed. The plans that are built, and what building each found, are in `docs/archive/`.

## Commands

```
pnpm install
pnpm test         # vitest: sweep, plan, fit, schema, golden scenes
pnpm typecheck    # tsc --noEmit, strict
pnpm test -u      # rewrite golden scenes; read the diff before committing it
pnpm bench        # the bench at localhost:5173, on Vite
pnpm --filter @unified-analytics/bench capture   # every sample × width × theme × height off the parts page, to apps/bench/captures/<time>/ (ignored by git); spec=<file> for a view that is no sample
pnpm --filter @unified-analytics/bench check     # hold the latest capture to the parts' promises (the fit rules, and cut, overlap, theme, steady); against=<capture> for what moved
pnpm --filter @unified-analytics/tokens generate   # rewrite packages/tokens/generated from its config
pnpm agent        # the agent surface as an MCP server over stdio: describe, check_view, draw_view
```

Packages export their TypeScript source and nothing is built for release yet. Vite serves the bench. CI runs `pnpm typecheck` and `pnpm test` on every pull request and on `master` (`.github/workflows/test.yml`); `bench.yml` builds and deploys the bench from `master` and runs neither.

## Layout

What each package is, and what about it the code does not say. A package's exports are in its `src/index.ts`.

- `packages/core`: no DOM and no framework. Types, presets and `expand`; the plan (`resolve`, which takes no size); the scene builders, in ratios; the fit rules and the one function that reads them at a room with no browser (`fitTo`, and `viewAt`, which follows a rule's fallback); `explain`, why a view looks as it does at a room; a facet's views (`facets`) and the board (`board.ts`); what each mark reads, as data (`reads.ts`), and which encoding each guide is read off (`guides.ts`); the registries for custom marks and for the presets their packages register; the sizes that no token and no rule says, in em of the view's type (`sizes.ts`); and JSON Schemas in `schema/` for a view, a catalog, a board and a scene (`scene/0`, a draft).
- `packages/dom`: the `<ua-view>` custom element and the fit-rule compiler. Its only dependency is core. It plans once with no limits, paints the ratio scene, and leaves the fitting to container queries; a measured pass (`measure.ts`) settles what CSS cannot say. One module per layout in `src/layouts/`, behind the seam in `src/layout.ts`. The furniture round the marks is in `src/chrome/`, each piece said once and painted by one function every layout calls. One interaction for every atom, and the names of the states an atom has, are in `src/rove.ts`. A custom mark's painter joins through `registerPainter`. `src/tokens.ts` lists the public tokens with the value each falls back to; gaps, gutters and heights are not tokens: they are in em of the view's type, as a fit rule's need is, so the two stay in step. It never imports `packages/tokens`, and meets it only in those names (`test/dom-tokens.test.ts`).
- `packages/fixtures`: the catalog, the seeded fixture query engine (`typical`, `no-prior`, `empty`), and the samples: the first six (`samples`), the ones added since (`moreSamples`), the ones with a `facet` (`facetSamples`, apart because a facet has no one plan for a sweep to ask for) and a board (`boardSamples`, apart because a board is no view). It registers the custom marks on import.
- `packages/geo`, `packages/flow`, `packages/partition`: the custom marks `geo` (a map, and the one package that depends on `d3-geo`), `link` (a Sankey of one step) and `partition` (a treemap). Each registers the preset that draws its mark, and its scene half loads with no DOM.
- `packages/tokens`: build-time token generation, in three tiers that Style Dictionary compiles to `generated/tokens.css`: base, common, and charts, which declares every `--ua-charts-*` token `<ua-view>` reads. `wpds.css` is a draft of the alias sheet for a page themed by the WordPress Design System.
- `packages/spacefast`: the adapter from one answer of Spacefast's analytics query API to a view's query, result and catalog (`adapt`). It knows that API's names; core still knows none.
- `packages/agent`: the agent surface, for an author outside this repository. `describe()` is what can be said, as data, and `check()` reads a spec with its answer and no browser: the refusal, or what the view says and shows at each room and why. It wraps core and adds no rule. `src/server.ts` offers both as an MCP server over stdio, with `draw_view`, which runs the bench's capture and check on a spec. The protocol is written out there, and it adds no dependency but `ajv`.
- `packages/dots`: not started.
- `apps/bench`: where work is looked at, and what GitHub Pages serves (`.github/workflows/bench.yml`). Every view is a `<ua-view>`. Its pages are the playground, the samples, a board, the marks, the parts and the tokens; a new page is built only once it is listed in `PAGES` in `vite.config.ts`, and paths in it are relative, so it builds for a subpath. The parts page shows one view at a ladder of widths. `capture.ts` takes those frames headless, each on one line so that none moves another, and `check.ts` holds them to what each part promises, read off `FIT_RULES` by core's own `fitTo`. Two captures of the same code agree frame for frame, so a frame that differs is a fault to find and not noise. Do not edit source while a capture runs: the dev server reloads the page under it.
- `test/`: one suite across the packages. There is no DOM in the run, so `packages/dom` is tested where it is strings and plain functions, and the element is checked in a browser on the bench. Nothing in the run places a node in pixels. Golden scenes are in `test/__snapshots__`. What the suites share is in `test/helpers.ts`, and the presets the library no longer ships, for the suites that exercise slots with them, in `test/examples.ts`: neither is itself a suite.
- `docs/archive/`: the plans that are built. They name things as they were then.

## Rules

- **The core has no DOM and no framework.** Runtime dependencies are `d3-scale`, `d3-shape` and `d3-array`. Ask before adding any other.
- **Do not add chart types.** A new shape is a mark. A new combination is written as its layers and kept as a sample in the bench: the library ships presets for the common charts only (reference, Decided 54), each named after the `@automattic/charts` component it replaces where one exists. What the grammar cannot say is a custom mark, registered in code (`registerMark`). A custom mark is a candidate for the system and not a way round it: it is held to what a core mark is held to, in `test/admission.test.ts`, which a new one must pass, and the count of them is a queue of candidates (reference, Decided 59).
- **New samples go in `moreSamples`.** `samples` is the first six, which `test/core.test.ts` holds by name and to the layouts they have. One with a `facet` goes in `facetSamples`: `resolve` refuses it, and the sweeps ask every sample for its plan.
- **Statistics come from the engine,** as companion fields (`metric@p25`). Core computes no quantile, bin or running total.
- **This is the candidate next major of `@automattic/charts`.** Keep its token structure, under our own prefix (`--ua-charts-*` for its `--a8c-charts-*`), and its keyboard model. The two do not interoperate yet; a page with version 4 tokens aliases each one across. See `docs/positioning.md`.
- **No sizes, breakpoints or presentation switches in a spec.** They belong to the container and its rules. A spec has no lever over them: where a default is wrong for a view, the answer is a better rule (reference, Decided 63).
- **A size is relative** (reference, section 10.2 and Decided 65). A fit rule's need, a size in `sizes.ts` and a size in a stylesheet of the element are in em: of the view's type, which every part of a view inherits, or of the face the size stands by. Where a part set in one face must line up with one in another, both take `em()` (`packages/dom/src/layout.ts`), the view's em handed down. `ch`, `lh` and a container's own units are as good. px is for a stroke, a hairline, a radius and what the measured pass reads, and `test/dom-tokens.test.ts` holds the stylesheets to that: a size added in px fails there.
- **Scenes carry paint tokens, never colours.**
- **A scene is the same on every machine.** Sums and products are, and a sine or a cosine is not, to its last digits: a place worked out with one goes through `steady` (`packages/core/src/path.ts`), to a millionth of its box. The golden scenes are held to the digit in CI, on another machine than the one that wrote them.
- **Keys are stable and unique.** Transitions and keyboard navigation hang on them.
- **A node says where it is in one vocabulary** (reference, section 11 and Decided 51): `x` and `y` where it is, `x2` and `y2` its other end, `w` and `h` an extent, whatever its kind and its layout. A node that is built takes these and no name of its own for a place. `x` runs across from the start and `y` up from the bottom, for every node. A change to how nodes are placed is checked by comparing every sample's scene before and after, node for node, and by the capture: golden scenes change shape with it and prove nothing.
- **The catalog is an input.** Core functions take it as an argument; nothing in `packages/core` knows a metric name.
- **Totals come from the engine.** A view never sums the rows it receives to make a tldr value.
- **A board is data, and a selection is a filter.** A board (`board/0`, `packages/core/src/board.ts`) is views and the part of the query they share: its `query` is its params, with no variable or expression, and it has no layout and no state apart from itself (reference, Decided 49). `boardViews` gives each view's spec and what it marks, and `boardSelect` the board after a view proposes a selection. Views are combined by one rule with no field: a view is filtered by every dimension of the board's `where` but the ones it draws. `<ua-view>` proposes the filter a datum is and how it was activated on `ua-select` (`detail.where`, and `detail.how`: `pick`, `toggle` or `extend`, by the modifier held), and marks by the filter set on `selected`. What a proposal does to the selection is core's `select`, never the view's: a host folds it in (Decided 50). The element draws no board and fetches nothing. `test/board.test.ts` holds it.
- **A filter is the engine's.** A query's `where` holds dimensions to values (reference, section 5 and Decided 48); the engine applies it and carries it back as `meta.where`, and `resolve` refuses an answer that is not of its query's filter. Core filters no row and sums none. A view says its filter after its sentence and in `explain`, read off the answer. The fixture engine answers it from its pairs, within limits it names. `test/where.test.ts` holds all of it.
- **Every error names the fix.**
- **A guide is read off a scale.** `packages/core/src/guides.ts` says which encoding each guide comes from, and the plan has a view's guides from it whatever the layout: a guide that is built is added there, not to a layout. A key (a legend, a ramp, a key to sizes) may not leave before the marks it keys: a rule that takes one puts a shorter form in its place (`show`, or a switch in `set` the layout draws), takes the marks too, or has them drawn without the encoding (`plain` in `GUIDES`). `test/guides.test.ts` holds every rule to it, and a new rule that takes a key early fails there. A plot's ramp, for a metric on `color`, has the legend's switch for its marks (`split: plain`): it leaves with the axes and the bars and dots are then in one paint. A legend with only its own one line to give way to (a divided list's, a band's, a circle's) has one ladder, `legend()` in `packages/core/src/fit.ts`, and `LEGEND_FIT` is that ladder's half of a stylesheet: a layout that gains such a legend takes both, with the least of its marks, and writes neither again (reference, Decided 66).
- **A mark reads what `READS` says.** `packages/core/src/reads.ts` lists the channels each mark reads in each layout and what each may hold (`READS`), the ones it is not drawn without (`NEEDS`) and the layer fields it has a use for (`FIELDS`), and `resolve` refuses what a layer says that is not there. A mark, a channel or a field that is built is added to it, and to the table in section 7 of the reference, in the same change. `test/reads.test.ts` holds the two together, and holds every cell to be one a sample draws or a probe there shows: add the probe with the cell. A custom mark states its own channels, in `reads`, and the fields it reads, in `fields`. `test/reads.test.ts` holds the fields true as it holds the channels.
- **A mark is one function of its space** (reference, Decided 44). A view's space is two axes, each a list of values, a quantity or nothing, flat or bent about a centre, and a layout says what stands round the marks, not which marks may be drawn. So a mark that comes to be drawn in a second layout is drawn there by the function it has, handed that layout's places (`GRID_MARKS`, `LIST_MARKS`, `ROUND_MARKS` and `OVER_MARKS` in `scene.ts`), and painted by the painter it has (`paintLabels` and `paintPaths` in `packages/dom/src/layouts/points.ts`). It is not written again. A row's track draws the plot's `bar`, `rule`, `tick`, `dot` and `unit` so: each is the plot's function, handed one row, and what it makes is turned once (`turn`, `turnLayer` and `inTrack` in `scene.ts`), with what a list alone does to a mark said after the turn. A custom mark that offers its places (`places` in `marks.ts`) takes the plot's `text` over it the same way. The grid, the list, the circle and the map are done, and each stage was held to the bench's capture frame for frame.
- **A scale's domain goes through `common`** (`packages/core/src/scene.ts`). The views of a facet are read against one another, so each takes the widest domain any of them would take alone, named on its result (`Result.domains`). A scale that is added, in core or in a custom mark, passes what it would take through `common(result, name, own)`, or a facet of it draws each view to its own top. A whole (the shares of a pie) is its own and does not. `test/facet.test.ts` holds a plot, a list and a circle to it.
- **How a view gives way is data, and one function reads it.** A plan takes no size. The fit rules say what each part needs and what goes without it, `fitTo` reads them at a room for any surface, and the element's stylesheet is the same rules compiled. So a rule names every part it takes, one that stands inside another among them, and says which kind of view it is for (`mark`, `has`). A need is in em, the size of the view's type: the element asks it in em, and `fitTo` takes a room in px with the size of an em (`em`, or `EM` where none is said). A layout's painter adds CSS under a rule (`fit`) for how what is left is arranged, never for which parts show, and makes no rules of its own. `test/fit.test.ts` holds every sample at every room to it: a view is its number alone wherever a rule takes its marks, and no key goes while its marks stay. What only measuring decides is listed in the reference, section 10.2, and is owed as rules (Open 19).
- **Proposed items** in the reference are the plan: build them as written and report if they do not hold up. **Open items** are not yours to settle: raise them with a recommendation.
- **Small commits,** one concern each.
